# Lockfile

`addons.lock` is generated by `gpm` and should be committed with
`addons.toml`. It records what was actually resolved and installed.

Each entry contains:

| Field | Meaning |
| --- | --- |
| `resolved_version` | Git commit SHA, GitHub release tag, or archive version marker. |
| `source_path` | Source subdirectory that was installed. |
| `checksum` | SHA-256 for archive and GitHub release downloads. |
| `spec_hash` | Hash of the manifest fields that affect resolution. |
| `slices` | Every slice ID the addon's index publishes, mapped to that slice archive's SHA-256. Set only for a sliced addon. |
| `artifacts` | Every format-2 shared artifact, mapped to that artifact archive's SHA-256. |
| `index_sha256` | SHA-256 of the raw `gpm-index.toml` bytes the `slices` table was read from. Set exactly when `slices` is set. |

An addon is either sliced or it is not: `checksum` and `slices` are never both
set, and a `slices` table must record the `core` slice.

## Sliced Addons

For an addon published as [platform slices](slices.md), `addons.lock` records
the whole **published** slice set rather than the slices this machine installed:

```toml
[addons]
  [addons.limboai]
    resolved_version = "1.4.0"
    source_path = ""
    spec_hash = "7f5c220d5f17347112379ba4773a6ae70cb7c8914b2175c03693862cc60d7af3"
    index_sha256 = "4a79717d9d4b2573188bb7396e10b37e5e5852531302542d3741dd00c67ff217"
    [addons.limboai.slices]
      "android.arm64" = "6e211f210f816965760abe4efd1c80936b15c95acf3e8a771312aacb1f4ed400"
      core = "e8de5ee7b224e7aa447885ec3c248f04151e111f5bd9f78bdbfc85aa25fbb8c4"
      "ios.arm64" = "6dff4908a2f07678af6f24f5719b58f4ede151a5ca0054bce98b8ac5ff21bfcd"
      "linux.x86_64" = "38186f3f2cfee3bb9afbab20f5b3f93290ff9e2e67589082707edcd5a8556e7d"
      macos = "2a3441a0f24f45b89d7ee14a7b4ddf4458bbbdf715e652155f8b6695b1d70514"
      "windows.x86_64" = "069e11e000677fb6ec865d66024b7bca8fa28098bcae3569c5ad6b8d64bb58c2"
```

Recording the published set is what keeps the lock machine-independent. Two
contributors on different hosts write the same table, and so does the same
project under `--all-platforms` or `--host-only`: the lock is byte-identical in
all three selection modes. Which slices a particular machine actually
materialized is a separate question, answered by `.gpm-state.toml`.

For a format-2 index, `artifacts` pins the complete published shared-artifact set
on every machine. An artifact ID is its generic platform name, so a selected
architecture slice of that platform pulls it in automatically. The selected
closure on one disk remains a `.gpm-state.toml` concern.

Upgrade every collaborator to a gpm release that supports index format 2 before
committing a lock with `artifacts`. Older gpm releases still reject a format-2
index when they fetch it, but their lockfile reader predates this table and may
drop these pins if it rewrites the shared lock without fetching.

```toml
[addons.sentry.artifacts]
  android = "8ffda2f9a5237ddc7551d0d34db55cf01b79260ad9943166a54d829f57100f7b"
```

`index_sha256` pins the index document itself, so a retagged release cannot
silently repoint the slice archives. On a locked install the fetched index digest,
the published slice and artifact sets, and every archive checksum are all
compared against the lock, whatever the selection mode.

`addons.lock` is the only verification authority. `.gpm-state.toml` records what
is on disk and never vouches for its contents.

## Install Behavior

`gpm install` compares the current manifest entry with the lock entry:

- If the hash matches, the lock pin is honored.
- If the hash differs or the entry is missing, the addon is re-resolved.
- On a full install, lock entries for addons no longer present in the manifest
  are removed.

For Git sources, a locked install fetches the exact commit SHA stored in
`resolved_version`.

For archive and GitHub release sources, checksums are verified when they are
available. A manifest `checksum` is checked on every fetch. A lockfile
`checksum` is checked when installing from an existing lock pin.

A consistent lock entry is honored only once `gpm` has also confirmed that this
machine holds the slices it needs, because the lock says nothing about this disk.
When the needed set and the recorded set differ in either direction, the addon is
re-fetched. The machine-local state also records the installed file paths. If one
of those files is missing, `gpm install` re-fetches and replaces the addon; it does
not hash file contents or reject additional files, so intentional in-place edits
do not cause a re-fetch loop.

## Update Behavior

`gpm update` ignores existing pins for the selected addons:

```bash
gpm update
gpm update dialogue_manager
```

Use `gpm update` when you intentionally want to move to newer refs or refresh
release/archive pins. Review the resulting `addons.lock` diff before merging.

## Remove Behavior

`gpm remove <name>` deletes the installed addon directory, removes the manifest
entry, and removes any lock entry for that addon.
